# Допущения и вопросы

Проектирование принято пользователем. Решения ниже применяются при реализации соответствующих этапов; их изменения должны отражаться в связанных документах.

## Принятые допущения

| ID | Решение | Основание и последствия |
| --- | --- | --- |
| D1 | Активного приглашенного сотрудника можно назначить до подтверждения почты | SPEC D говорит «активных приглашенных», а не только подтвердивших. invited_at обязателен, адрес проверен. Он входит в статистику получателей, но не входит в приложение до активации. Отключенные исключены |
| D2 | Управление пользователями, ролями и группами нельзя делегировать обычной роли | SPEC B говорит «только администратор», а C допускает выбор permissions. Выбрана более узкая трактовка: административные коды зарезервированы системной роли; обычные роли могут получать рабочие, chat и audit permissions. Делегирование этой власти требует отдельного решения |
| D3 | Повторное назначение восстанавливает только совместимый текущий прогресс | Старые отметки/завершение не удаляются из истории. Для неизмененных подзадач восстанавливаются отметки; новые/измененные становятся пустыми по content_revision. Завершение восстанавливается только если прежний completion_epoch совпадает с текущим progress_epoch и все текущие подзадачи выполнены. Иначе сохраняется история, но current completed_at очищается. Автор видит это до подтверждения. Так прошлое завершение не обходит новые требования |
| D4 | Архив не дает доступа бывшему исполнителю после отзыва | «Авторизованные участники» в SPEC E трактуется как пользователи с текущим основанием чтения. Отзыв в G требует прекращения доступа сразу. Архив сохраняет историю, но не возвращает доступ; независимое авторство/view_all остается |
| D5 | Снятие управленческой роли убирает права автора по permission, но не личное назначение | Авторство неизменно, но own просмотр/редактирование требуют текущих permissions. Если автору самому выдано Assignment, его личный доступ сохраняется. Это не постоянный доступ по факту прошлой роли |
| D6 | Все назначения/содержательные записи сериализуются через AccessGuard в V1 | Предполагается небольшой внутренний сервис. Конкурентные чтения допускаются через shared lock; изменение прав и записи — exclusive lock. Цена — ограниченный throughput, выигрыш — ясная гарантия отзыва и последнего администратора. Перед запуском проверить нагрузку; увеличение масштаба требует нового решения по блокировкам |
| D7 | Чат можно закрыть, архивировать задание; открыть обратно/разархивировать нельзя в V1 | ТЗ не задает этих переходов. Закрытый чат можно модерировать, архив — только читать. Системный отзыв доступа разрешен в архиве |
| D8 | Почта нормализуется целиком lowercase; после приглашения не меняется в V1 | ФИО/имена ролей и групп можно переименовывать. Уникальность почты включает отключенных. Замена email потребовала бы нового приглашения и отзыва доступа; такой workflow пока не заявлен |
| D9 | Ввод срока только датой означает последний момент этого московского дня | UTC хранится timezone-aware; UI объясняет конец дня. Event datetime отдельно. Все сроки обязательны; ближайшие сверху, при равенстве tie-breaker по id |
| D10 | При создании нужен хотя бы один получатель, а ноль возможен после отзывов | Нет отдельного lifecycle черновика. Для нуля показывается «Нет исполнителей»; частично выполненные подзадачи не увеличивают процент; экранный процент округляется до целого |
| D11 | Свой прогресс меняет только исполнитель, даже администратор | Глобальное изменение относится к содержанию и назначениям, а не отметке от чужого имени. Массовый сброс при изменении подзадач допустим строго по SPEC E с подтверждением и аудитом |
| D12 | Одно событие — один общий чат; подписи используют текущие активные группы автора сообщения | Пересечения назначений не создают отдельные чаты. Показ групп не дает membership-права и не открывает полный список исполнителей. История не обязана сохранять старую подпись групп |
| D13 | Приглашение 48 часов, recovery 1 час, чат 4000 символов/50 сообщений на страницу | Это серверные настраиваемые лимиты, отсутствующие в SPEC. Rate-limit значения и polling описаны в ARCHITECTURE, проверяются на этапах 2 и 6 |
| D14 | Бизнес-история в V1 не удаляется автоматически | Пользователи/справочники отключаются, задания архивируются, подзадачи мягко удаляются, аудит append-only. Персональные данные не создаются для студентов. Сроки юридического хранения/удаления нужно уточнить до production, не изобретать сейчас purge |
| D15 | Обычные роли могут получать audit.view, но payload чужих заданий фильтруется | Audit permission разрешает каталог метаданных изменений; содержимое доступно только при объектном чтении. Исходный текст скрытого чата доступен лишь системному администратору с audit.view, не обычному аудитору/модератору |

## Вопросы, действительно блокирующие проектирование

**Не выявлены.** SPEC задает стек, предметную область, роли, корпоративный домен и ключевые правила достаточно подробно. Для неоднозначностей зафиксированы ограничительные допущения D1–D15; модель не зависит от выбора провайдера SMTP или хостинга. Не требуется ждать ответа, чтобы завершить этап 0.

Если любое из допущений не соответствует процессу колледжа, его следует изменить перед реализацией соответствующего этапа. Это возможность уточнения, а не требование ответить сейчас на весь перечень.

## Параметры, нужные перед production, но не блокирующие проектирование

| ID | Что понадобится | Когда и что блокирует |
| --- | --- | --- |
| P1 | Домен сервиса, платформа размещения, оператор TLS, разрешенные hosts/proxy | Этап 7: внешний HTTPS-запуск; локальная архитектура и тесты продолжаются без этого |
| P2 | Реальный SMTP, sender и доступные корпоративные правила доставки; адрес первого администратора | Перед production bootstrap и проверкой реальной активации. Значения credentials — только в защищенных настройках, не в чате/Git; Mailpit разблокирует development |
| P3 | Требуемые RPO/RTO, место хранения/доступ к backup и сроки хранения/удаления персональных данных и аудита | До production-приемки. Предварительно ежедневный dump, 30 дней backup, без автоматического удаления бизнес-истории; это не согласованный SLA. Более строгий RPO может потребовать WAL/PITR и изменения операционной схемы |
| P4 | Ожидаемое число сотрудников и одновременных активных сессий | До приемки нагрузки на этапе 7; нужно проверить выбранную простую синхронизацию и подобрать workers/лимиты. Не требуется для логической модели, но большое значение может изменить D6 |

Пользователь принял этапы 1–4 и разрешил этап 4. Development использует Mailpit; внешний SMTP, HTTPS и публикация production остаются этапом 7. Реальные секреты в чате/Git не запрашиваются.
