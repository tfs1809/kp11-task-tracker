# Права доступа

Статус: проектная политика для версии 1, код еще не реализован. Основание: SPEC B, C, E–H; схема — [ARCHITECTURE.md](ARCHITECTURE.md), спорные трактовки — [DECISIONS.md](DECISIONS.md).

## 1. Общие правила

1. По умолчанию запрещено. Запрос требует активного аккаунта, подтвержденной почты и действующей сессии; далее проверяются permission и связь с объектом.
2. Права активных ролей объединяются. Снятая/отключенная роль перестает участвовать немедленно. Членство в AudienceGroup не дает ни одного permission и не создает Assignment автоматически.
3. Личное назначение дает базовые действия исполнителя без специальной роли. Даже руководитель/администратор работает со своим назначением на общих условиях; чужие чекбоксы вручную не меняет никто.
4. Администратор — активная защищенная системная роль, а не произвольная роль с названием «Администратор». Он имеет все перечисленные управленческие права, но не обход ограничений архива, закрытого чата, валидации, аудита и последнего администратора.
5. Просмотр и изменение независимы. Любая операция с объектом сначала требует доступного чтения объекта. `edit_all` без `view_all` не раскрывает новые объекты; действует только на объекты, к которым уже есть доступ по другой связи.
6. Авторство само по себе не гарантирует управленческий доступ после снятия роли: для собственных выданных нужны `view_own`, для редактирования — соответствующее разрешение. Если у автора есть действующее личное назначение, доступ исполнителя сохраняется независимо.

## 2. Каталог permission и начальные роли

Обозначения: А — Администратор, Р — Руководитель, К — Куратор, П — Преподаватель. `✓` — начальное разрешение, `—` — не выдано. Администратор имеет полный каталог через системную роль; другие роли настраиваются в указанных пределах.

| Код | Русское название / область | А | Р | К | П | Настройка новых ролей |
| --- | --- | --- | --- | --- | --- | --- |
| `workitems.create` | Создание задач и событий | ✓ | ✓ | — | — | Да |
| `workitems.view_own` | Просмотр собственных созданных заданий, исполнителей и прогресса | ✓ | ✓ | — | — | Да |
| `workitems.edit_own` | Изменение текста, срока и подзадач своих; архив и закрытие чата | ✓ | ✓ | — | — | Да |
| `workitems.manage_own_assignees` | Управление исполнителями своих заданий | ✓ | ✓ | — | — | Да |
| `workitems.view_all` | Просмотр всех заданий, прогресса и чтение чатов | ✓ | — | — | — | Да |
| `workitems.edit_all` | Изменение всех доступных заданий и их исполнителей | ✓ | — | — | — | Да; не дает `view_all` |
| `accounts.manage_users` | Приглашение/переотправка, имена, отключение/реактивация сотрудников | ✓ | — | — | — | Зарезервировано администратору |
| `access.manage_roles` | Создание/имена/активность ролей, разрешения и назначение ролей | ✓ | — | — | — | Зарезервировано администратору |
| `audiences.manage_groups` | Создание/имена/активность групп и членство | ✓ | — | — | — | Зарезервировано администратору |
| `discussions.moderate` | Скрытие сообщений с причиной в доступных событиях | ✓ | — | — | — | Да; не дает чтения всех событий |
| `discussions.send_accessible` | Отправка в доступный открытый чат без авторства/назначения | ✓ | — | — | — | Да; отдельное право для случая SPEC G |
| `audit.view` | Просмотр журнала аудита | ✓ | — | — | — | Да; не дает доступ к оригиналам скрытых сообщений |

Создание требует также `view_own` и `manage_own_assignees`, поскольку в V1 нет задания без выдачи и автор должен проверить отправку. `edit_own`/`manage_own_assignees` требуют читаемого собственного задания; интерфейс сообщает зависимость. Система не дописывает отсутствующие разрешения молча. Код каталога неизменяем, новые коды вводит разработчик.

Ограничение только администратора на пользователей/роли/группы сохраняет буквальное требование SPEC B. В UI эти зарезервированные коды видны с пояснением, но недоступны для выдачи обычной роли; подмена POST не меняет это. Если позднее потребуется делегирование этой власти, необходимо отдельно изменить ТЗ и угрозы повышения привилегий (D2).

## 3. Матрица действий над объектом

Для столбцов ниже «Автор» — пользователь с `view_own` и нужным own-permission; «Исполнитель» — действующее назначение; «Глобальный читатель» — `view_all`; «Глобальный редактор» — `edit_all` и доступное чтение. Совмещение ролей/связей складывает возможности. Для управляющих действий объект должен быть неархивным.

| Действие | Исполнитель | Автор | Глобальный читатель | Глобальный редактор | Администратор |
| --- | --- | --- | --- | --- | --- |
| Читать карточку / общий текст / сроки | Да, своего назначения | Да | Да | При имеющемся чтении | Да |
| Читать свой личный прогресс | Да | Если сам назначен | Если сам назначен | Если сам назначен | Если сам назначен |
| Читать список исполнителей, статистику и чужой прогресс | Нет | Да | Да | Только с `view_own`/`view_all`, а не из edit | Да |
| Менять свои отметки | Да, до завершения | Только если сам назначен | Только если сам назначен | Только если сам назначен | Только если сам назначен |
| «Выполнено» / «Вернуть» | Да, свое | Только если сам назначен | Только если сам назначен | Только если сам назначен | Только если сам назначен |
| Менять чужие отметки или вручную завершать за другого | Нет | Нет | Нет | Нет | Нет |
| Менять заголовок, описание, срок, подзадачи | Нет | `edit_own` | Нет | Да | Да |
| Добавлять/отзывать/восстанавливать исполнителей | Нет | `manage_own_assignees` | Нет | Да | Да |
| Подтверждать сброс прогресса при изменении подзадач | Нет | `edit_own` | Нет | Да | Да |
| Архивировать | Нет | `edit_own` | Нет | Да | Да |
| Читать доступный архив | Да, если доступ не отозван | Да | Да | При имеющемся чтении | Да |
| Выполнять/изменять содержание/чат в архиве | Нет | Нет | Нет | Нет | Нет |
| Читать чат события | Да | Да | Да | При имеющемся чтении | Да |
| Отправлять в открытый чат события | Да | Да | Только `send_accessible` | Только автор/исполнитель или `send_accessible` | Да |
| Закрыть чат | Нет | `edit_own` | Нет | Да | Да |
| Скрыть сообщение с причиной | Только с `moderate` | Только с `moderate` | Только с `moderate` | Только с `moderate` | Да |
| Читать оригинал скрытого сообщения | Нет | Нет | Нет | Нет | Да, с `audit.view` |

Скрытие сообщения требует readable event + `moderate`, но не требует открытого чата: в закрытом неархивном чате модерация допустима. `moderate` сам по себе не разрешает отправлять: для этого нужен `send_accessible` или авторство/назначение. Архив — только чтение; разархивирование и повторное открытие чата в V1 не предусмотрены.

Глобальный читатель получает общий прогресс, но не административные данные пользователей. Коды разрешений для создания/изменения не позволяют менять автора, тип после выдачи, создавать student сущности или произвольные permissions. WorkItem и Assignment ищутся по разрешенной выборке; знание UUID ничего не разрешает.

## 4. Управление справочниками и учетной записью

| Действие | Действующий сотрудник | Системный администратор |
| --- | --- | --- |
| Читать свои ФИО/корпоративную почту/группы/роли | Да | Да |
| Сменить свой пароль / выйти | Да | Да; пароль другого не устанавливает |
| Изменить собственные роли/группы/активность через профиль | Нет | Только через аудируемые административные операции |
| Пригласить, переименовать, отключить/реактивировать сотрудника | Нет | `manage_users`; не последнего действующего администратора |
| Менять корпоративную почту после приглашения | Нет | Нет в V1; требуется отдельный lifecycle подтверждения |
| Создать/переименовать/отключить роль, выбрать permissions, назначить роль | Нет | `manage_roles`; системные атрибуты неизменяемы; защитить последнего администратора |
| Создать/переименовать/отключить группу, изменить Membership | Нет | `manage_groups` |
| Читать полный справочник пользователей | Нет | Да |
| Выбирать ФИО/роли/группы получателей при разрешенной выдаче | По разрешению создания/управления исполнителями; ограниченный selector | Да |
| Читать AuditEntry | Только если выдан `audit.view` | Да |

Сотрудник с `audit.view` видит изменения разрешенного audit-каталога, включая ФИО акторов, ids объектов и разрешенные изменения, но не получает через аудит рабочие тексты заданий, к которым нет объектного чтения. Audit selector редактирует payload: для недоступных объектов только метаданные. Оригиналы чата исключены из AuditEntry вообще. Администратор видит полный разрешенный payload истории. Пароли, ссылки, токены и cookie не доступны никому через приложение.

## 5. Отзывы, архив и HTTP

- Отключенный/неподтвержденный пользователь не получает рабочие данные; неактивные сессии не обходят проверку. После снятия роли доступ по этому permission пропадает; доступ исполнителя остается, если Assignment действует.
- Отозванное назначение убирает личную карточку и чат, включая архив. Если человек одновременно автор с правами или глобальный читатель, эти независимые основания чтения остаются. Завершенное, но неотозванное назначение сохраняет чат.
- Группа/роль, использованная как аудитория при отправке, не является текущим основанием доступа: основание — конкретное Assignment. Изменение Membership не отзывает и не добавляет старые назначения.
- Архив читают только пользователи с текущим основанием чтения; прошлое участие не дает постоянного доступа. Отключение аккаунта и системный отзыв назначения разрешены и в архиве, поскольку это операции доступа, не редактирование содержания.
- Все изменения POST с CSRF; GET только чтение. Нет приема `actor_id`, `author_id`, `assigned_by`, `is_admin`, `completed_at`, `permission` из формы как доверенных данных. Исполнитель не передает произвольный user_id для выбора чужого прогресса.
- Неавторизованный HTML-запрос уходит на вход; polling получает 401. Недоступный объект возвращает 404, запрещенное действие над видимым объектом — 403; конфликт версии/ключа — 409, превышение лимита — 429. Проверяется не только detail, но и списки, фильтры, статистика, превью получателей, audit, пагинация и повторы запросов.
- Служебные services всегда перечитывают текущие права под блокировкой; кэш прав между запросами не используется. UI может скрыть кнопку, но серверная проверка от этого не зависит.

## 6. Обязательные отрицательные проверки

На PostgreSQL и через реальные HTTP endpoints проверить: подмену ids назначения/подзадачи/чата, получение общего списка исполнителем, создание роли/членства прямым POST, edit при одном view_all, view чужой задачи при одном авторстве другой, send при одном view_all/moderate, просмотр скрытого текста модератором, чтение архива после отзыва. Проверить отключение с открытой страницей, повторный idempotency-запрос после отзыва, конкурентное лишение двух администраторов и конкурентный отзыв с записью. Все эти сценарии входят в PLAN; здесь не утверждается их выполнение.
