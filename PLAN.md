# План реализации и приемки

Выполнены этап 0 (проектирование) и этап 1 (основа проекта); результаты проверок — в STATUS.md. Этапы 2–7 не начаты. Приложение нельзя считать готовым по факту завершения одного этапа или успешного старта процесса.

Документы: [SPEC.md](SPEC.md), [ARCHITECTURE.md](ARCHITECTURE.md), [PERMISSIONS.md](PERMISSIONS.md), [DECISIONS.md](DECISIONS.md), [STATUS.md](STATUS.md).

## Порядок работы

Этапы последовательны; аудит, проверки прав и транзакции входят в каждую добавляемую операцию, а не откладываются до финала. Репозиторий и lockfile изменяются только в пределах согласованного этапа. После этапа обновляются STATUS и связанные решения: реализованное, реально запущенные команды, количество/результаты тестов, ограничения, ручная проверка. Не запущено, пропущено, ожидаемый отказ и ошибка различаются.

Приведенные ниже команды и сценарии — будущие критерии, не результаты уже выполненных проверок. Конкретные команды фиксируются в README после появления соответствующих файлов. Нужные тесты выполняются на PostgreSQL 17; SQLite не заменяет UNIQUE, составные FK и блокировки. Django TransactionTestCase с отдельными соединениями нужен для конкурентных сценариев, обычный TestCase — для остальных. Браузерные сценарии проверяют настоящие серверные данные, без localStorage/mock-базы.

## Этап 0. Проектирование — выполнен

Результат: границы, выбранный стек, модульные слои, схема данных и ограничения, lifecycle, политика доступа, транзакции, история, этапы и критерии, допущения. ТЗ сохранено как исходный документ.

Приемка: нет кода приложения; покрыты SPEC A–K; роли отделены от групп; Assignment хранит персональный прогресс; определены отзыв доступа, защита последнего администратора, конкурентные действия и архив. Блокирующие вопросы перечислены отдельно, без смешения с параметрами production. Проверены официальные источники и внутренние ссылки; реальные runtime-проверки еще невозможны.

Ручная проверка: прочитать три основных документа и DECISIONS, сопоставить с SPEC. Изменение проектного решения корректирует связанные документы до реализации.

## Этап 1. Основа проекта и воспроизводимая среда — выполнен

Реализовать:

- Django-проект с шестью apps, отдельными dev/test/production settings; ранняя кастомная User до первой миграции, базовые AuditEntry и AccessGuard.
- Точные lock-зависимости с хешами, проверенные версии и digest образов. Compose с web/PostgreSQL/Mailpit, named volume, pg_isready, явными миграциями. `.env.example` без секретов, `.gitignore`, README запуска.
- Базовый русский layout, общие pages/errors; внутренние readiness/liveness checks без рабочих данных; PostgreSQL test configuration.
- Каркас транзакционного service/policy/selector, закрытый по умолчанию доступ, запрет универсального Django Admin CRUD. Документированный миграционный пользователь и отдельный runtime DB user.

Критерии: чистая установка и миграции воспроизводятся; повторный запуск не теряет запись в PostgreSQL; mail backend доставляет тестовое письмо в Mailpit; настройки production не допускают DEBUG и тестовую почту. Проверить Django system checks, check миграций, реальный HTTP smoke приложения и запрос БД; отсутствие бизнес-тестов не выдается за их успех. Не использовать отключение TLS, checksum или package signature.

Ручная проверка: по README поднять Compose, выполнить миграции, посмотреть тестовое письмо, перезапустить web/db и проверить сохраненную development-запись. В cloud использовать существующий checkout, не создавать worktree. При недоступности Docker сначала диагностировать capability; не объявлять Compose проверенным на основании локального Python.

## Этап 2. Сотрудники, права и безопасный вход

Реализовать:

- Role/Permission/UserRole, AudienceGroup/Membership; seed четырех ролей и трех заданных групп; защищенный каталог permissions и административные forms/services.
- Корпоративная нормализация/уникальность email, приглашение и переотправка, активация с собственным паролем, локальный bootstrap, login/logout, reset/change password, DB sessions/auth_version.
- Общие лимиты запросов, CSRF и no-store, секреты вне журналов; короткие блокировки и audit каждого административного изменения.
- Раздел «Мои задачи» для каждого действующего пользователя пока с честным пустым состоянием. Никаких фиктивных задач.

Критерии: чужой адрес сам по себе не активирует аккаунт; принимается только точный corp.kp11.ru без учета регистра, дубликаты отклоняются; нет открытой регистрации/default-пароля. Просроченная/отозванная/повторная ссылка отклоняется, два конкурентных POST активируют только один раз. Повторная отправка отзывает предыдущую ссылку. Reset не раскрывает существование пользователя и отзывает все старые сессии; отключение прекращает доступ с уже открытой страницы. Права нескольких ролей объединены, Membership их не выдает. Прямой POST не назначает себе роль; два конкурентных административных запроса не оставляют ноль действующих администраторов. Отключение системной роли защищено так же, как отключение аккаунта.

Ручная проверка: bootstrap через документированную команду → письмо Mailpit → пароль → вход; пригласить второго администратора и сотрудника, снять роль/отключить аккаунт, проверить вторую открытую сессию. Логи не должны содержать ссылки/пароли/токены.

## Этап 3. Выдача задач и событий, snapshot получателей

Реализовать:

- WorkItem/Assignment, Subtask, selections/sources, ограничения/индексы; поля события и отдельный срок.
- Выбор пользователей/ролей/групп по ИЛИ, dedup, server preview с итоговыми ФИО и количеством; подтверждение актуального списка.
- Транзакционную выдачу и MutationReceipt, own/all selectors; неизменяемые author/kind; первичную выдачу с минимум одним получателем.

Критерии: сотрудник с двумя ролями/группами получает ровно одно Assignment, все причины назначения сохранены; изменение состава группы после отправки не меняет получателей. Изменение между preview и submit требует повторного подтверждения; сервер не доверяет ids из JS. Повтор формы не создает задание/назначения повторно; другой payload с прежним ключом дает конфликт. Автор не получает чужую задачу без дополнительного основания. Событие хранит event_at отдельно от due_at; у task нельзя создать чат. Проверить UTC/московский срок по дате.

Ручная проверка: руководитель выдает task/event по комбинации ролей и групп, сравнивает получателей с preview, обновляет состав группы, повторяет отправку и пробует недоступные URL под другим сотрудником.

## Этап 4. Личный прогресс, редактирование, статистика и архив

Реализовать:

- SubtaskProgress и составные FK, отметки, выполнение/возврат, версии форм, progress_epoch и content_revision.
- Изменение содержания/порядка с превью сброса и подтверждением; добавление/отзыв/восстановление исполнителя с историей.
- Статистику и detail прогресса для автора/глобального читателя, архив только для чтения, историю действий, деактивацию с отзывом Assignment.

Критерии: действия одного исполнителя не меняют другого; частичные отметки не позволяют завершить; без подзадач завершение возможно сразу. «Вернуть» сохраняет чекбоксы и историю завершения. 3/5=60%, ноль без деления; отозванные/неактивные исключены. Переименование задания, срок и reorder не сбрасывают; добавление/изменение подзадачи снимает completion только по правилам, остальные отметки сохраняются. Удаление не завершает автоматически. Подтверждение старых последствий не принимается, конфликт версий не перезаписывает данные. Повторное назначение сохраняет совместимый старый прогресс с предупреждением; реактивация аккаунта ничего сама не восстанавливает. Прямая вставка progress к чужому WorkItem отклоняется БД. Архив и отзыв не превращаются в обход доступа.

Ручная проверка: два исполнителя независимо проходят checklist, руководитель смотрит статистику, меняет/переставляет/удаляет подзадачи, отзывает и возвращает сотрудника, архивирует. Проверить конфликт двух открытых форм. Автотесты дополнительно синхронизируют выполнение/сброс и отзыв/выполнение через отдельные соединения.

## Этап 5. Полный рабочий интерфейс

Реализовать: русские «Мои задачи» с двумя вкладками, фильтрами и сортировкой; «Выданные», отдельно «Все задания» по праву; карточку назначения, «Все исполнители»/«Не выполнили»; доступный архив; административные страницы; mobile CSS, сообщения ошибок/пустые состояния и сохранение ввода.

Критерии: серверные списки/фильтры не выдают чужие данные; исполнитель получает только свои marks, не скрытую HTML-таблицу общего прогресса. Кнопки соответствуют серверным правам. Ключевые сценарии в браузере на 360 px и 1280 px: приглашение/вход, выдача, отметки, выполнение/возврат, редактирование со сбросом, отзыв и архив. Нет горизонтального scroll основной страницы; keyboard-only navigation, labels/focus, contrast и текстовые статусы проверены. Без JavaScript обычные формы выдачи/выполнения работоспособны; preview допускает отдельную серверную страницу подтверждения.

Ручная проверка: пройти эти сценарии как руководитель и исполнитель на телефоне/ПК, в том числе с длинными ФИО и текстами, ошибкой формы и ближайшим/просроченным сроком.

## Этап 6. Чат события и модерация

Реализовать: EventMessage, cursor pagination/polling, текущие группы автора сообщения, лимиты и MutationReceipt отправки; close-chat, скрытие с причиной, отдельный администраторский доступ к оригиналу. Без редактирования сообщений, вложений и почтовых уведомлений о них.

Критерии: автор и действующие исполнители читают/пишут; view_all дает только чтение; send_accessible и moderate имеют разные действия и требуют доступного события. Завершение Assignment не закрывает чат, отзыв сразу закрывает доступ. HTML/XSS показывается текстом; пустой/слишком длинный текст отклоняется, лимит дает 429. Повтор запроса не дублирует сообщение и не выдает его после отзыва. Новые/старые страницы используют устойчивый cursor, изменения не теряются на границе порций; скрытие старого уже показанного сообщения заменяет его заглушкой при следующем polling. hidden-original не появляется в обычном HTML/JSON/аудите/логах. Закрытый чат читается, но писать нельзя; архив только чтение. Несколько workers используют общий rate limit.

Ручная проверка: два сотрудника общаются в одном событии, обновляют историю, руководитель закрывает чат, модератор скрывает сообщение; отозвать назначение при открытой странице и проверить следующий запрос. Попробовать HTML, повтор POST и чат task через прямой URL.

## Этап 7. Развертывание, восстановление и общая приемка

Реализовать/завершить: production settings/Compose override, Gunicorn/HTTPS proxy, static, разделение DB-прав, инструкции SMTP, deploy/rollback, backup/restore и безопасной аварийной процедуры. Запустить полную business/HTTP/concurrency/browser suite и production checks. Убедиться, что тестовые fixtures/почта выключены, нет реальных секретов/сотрудников в Git.

Критерии: данные переживают перезапуск; выполнить настоящий dump/restore в отдельную БД и проверить назначения, прогресс, сообщения и аудит, а не только завершение утилиты с кодом 0. `manage.py check --deploy` на production settings без необъясненных замечаний; HTTPS/cookie/CSRF/hosts/rate limits, ограниченная учетная запись БД и журналы проверены. Все SPEC K1–K13 имеют результат, включая отрицательные и конкурентные случаи. Browser suite реально проходит на мобильной и desktop ширине, с зафиксированным числом тестов. До внешнего production-запуска нужны параметры P1–P4 из DECISIONS; секреты вводятся только в защищенные настройки.

Ручная проверка: по инструкции восстановить dump в отдельное окружение с тестовой почтой; пройти выдачу → выполнение → чат → отзыв. Проверить недоступность БД снаружи, HTTPS и отсутствие тестовых пользователей в production. Если внешняя среда/SMTP недоступна, отдельно записать непроверенные production-операции; локальная готовность не объявляется успешным production-развертыванием.
