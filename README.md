# Трекер задач колледжа

Внутренний веб-сервис для сотрудников колледжа. Этапы 1–5 приняты и зафиксированы коммитами `34b12bb`, `f34e6b1`, `d3854b7`, `ba89479` и `7b6f134`. Доступны выдача задач/событий, персональный прогресс, подтвержденное редактирование, управление исполнителями, статистика, история и архив. Этап 5 добавляет адаптивный русский интерфейс, вкладки и серверные фильтры. Этап 6 реализует чат событий: историю и polling, текущие группы автора, безопасные повторы, общие лимиты, закрытие и модерацию. Пользователь разрешил коммит и публикацию всех изменений; результаты проверок — в STATUS.md.

## Запуск development

Для **Docker Desktop на Windows / PowerShell** используйте [пошаговую инструкцию](WINDOWS_DOCKER_DESKTOP.md): подготовка, запуск, первый администратор, проверки и сохранение данных.

Нужны Docker Engine с Compose v2 и Python 3 для генерации локального `.env`. Проверено на Linux amd64, Docker 28.4.0/Compose 2.40.3. Python приложения находится в закрепленном Docker-образе; Node, локальный PostgreSQL и активация host-venv не нужны.

Из каталога репозитория:

```bash
python3 scripts/init_dev_env.py
docker compose build web
docker compose up -d --wait db mailpit
docker compose run --rm migrate
docker compose up -d --wait web
python3 scripts/smoke.py
```

`.env` создается со случайными локальными development-секретами и правами 0600, не выводится и не перезаписывается. Если уже существует свой `.env`, заполните пустые значения из `.env.example` самостоятельно. Не храните этот файл в Git. Compose не читает значения из `.env.example` автоматически.

**В текущей cloud-среде** home недоступен для записи Buildx, а TLS proxy требует системный CA. Вместо обычной команды сборки выполните:

```bash
export BUILDX_CONFIG="$PWD/.cache/buildx"
docker compose -f compose.yaml -f compose.cloud.yaml build web
```

Остальные команды те же. Overlay использует `/etc/ssl/certs/ca-certificates.crt` как временный BuildKit secret только при установке зависимостей; CA не копируется в образ и репозиторий. TLS и `--require-hashes` остаются включены. Обычная сборка без overlay в среде без этого proxy здесь не проверялась.

Web доступен локально на порту 8000, Mailpit — 8025; обе привязки только к `127.0.0.1`. PostgreSQL не публикует порт. Порты меняются через `WEB_PORT`/`MAILPIT_PORT` в `.env`; передайте соответствующие `--web-port`/`--mailpit-port` в smoke.py. Это локальные адреса для ручной проверки, не опубликованный cloud-preview. `PUBLIC_BASE_URL` задает фиксированный адрес сервиса для почтовых ссылок (по умолчанию `http://localhost:8000`); при изменении web-порта поменяйте его в `.env`. В production требуется явный HTTPS origin с host из ALLOWED_HOSTS; адрес не берется из HTTP Host.

Остановка и повторный запуск:

```bash
docker compose down
docker compose up -d --wait db mailpit
docker compose run --rm migrate
docker compose up -d --wait web
```

`down` сохраняет named volumes. Не используйте `down -v` для данных, которые нужно сохранить. Не меняйте DB-пароли в `.env` после инициализации volume без отдельной смены пароля роли в PostgreSQL: init-скрипт запускается только на пустом volume. Web не запускает миграции автоматически. После изменения кода пересоберите web и выполните явную команду migrate перед `up`.

## Проверки этапов 1–6

```bash
docker compose exec -T web python manage.py check --database default
docker compose run --rm migrate python manage.py makemigrations --check --dry-run
docker compose exec -T web python -m pip check
docker compose run --rm tests
python3 scripts/smoke.py
docker compose exec -T web python scripts/check_production.py
docker compose exec -T web python manage.py collectstatic --noinput
```

`tests` создает и удаляет отдельную `test_kp11`, использует миграционную учетную запись, затем проверяет ограничения runtime-роли и настоящие PostgreSQL row locks. Тестовые сотрудники существуют только в тестовой БД. Suite включает проверки каркаса и сотрудников/прав/auth: одноразовые ссылки, отзыв сессий, права, CSRF, версии форм и PostgreSQL concurrency. Дополнительно проверяются выдача, подпись и срок превью, OR/dedup, источники, неизменяемая история, idempotency, ограниченные object selectors и конкурентные подтверждения. Этап 4 проверяет независимые отметки, завершение/возврат, версии, сброс/восстановление, статистику, отзыв/архив и обновление заполненной БД. Этап 5 дополнительно проверяет фильтры/вкладки/пагинацию, сохранение ввода при возвращении из превью и отсутствие чужих объектов/данных в списках. Этап 6 дополнительно проверяет права чата, историю, безопасные повторы, модерацию и общие PostgreSQL-лимиты. `smoke.py` проверяет реальные HTTP HTML/CSS, закрытый health, запрос к БД и получение нового SMTP-письма именно текущего запуска через Mailpit API.

`check_production.py` загружает production settings с несекретными примерами домена/SMTP и запускает `check --deploy --fail-level ERROR`. Это проверка конфигурации, без подключения к SMTP/HTTPS. Остается явное предупреждение `security.W021`: HSTS preload выключен до решения для реального production-домена. `--fail-level WARNING` возвращает 1 из-за этого предупреждения; оно не скрыто и не обозначено как отсутствие замечаний. Остальные ошибки должны приводить к ненулевому коду.

## Первый администратор и ручная проверка этапа 2

На обычной development-БД первый администратор намеренно не создан. Запустите локальную команду, указав свой точный корпоративный адрес и ФИО:

```bash
read -r -p 'Почта первого администратора (corp.kp11.ru): ' bootstrap_email
read -r -p 'ФИО первого администратора: ' bootstrap_name
docker compose exec -T web python manage.py bootstrap_admin --email "$bootstrap_email" --full-name "$bootstrap_name"
```

Команда не принимает/выводит пароль или ссылку. Она запускается один раз и отправляет приглашение через SMTP. При неподтвержденной доставке приглашение остается в БД. После исправления SMTP повторите ту же команду с `--resend`: это допустимо только для того же еще не активированного адреса, прежняя ссылка отзывается. Повторный bootstrap после активации запрещен; HTTP bootstrap/registration отсутствуют. Пароли действующих сотрудников администратор не задает.

1. Откройте локальный Mailpit `http://127.0.0.1:8025/`, найдите приглашение на свой адрес, перейдите по ссылке, задайте собственный пароль из минимум 12 символов и войдите. На главной должны быть ФИО, роли/группы и «Задач пока нет». Повторная активация той же ссылки должна отклоняться.
2. Через «Администрирование» пригласите второго администратора и обычного сотрудника. Активируйте их через соответствующие письма; войдите ими в отдельных профилях/приватных окнах. Назначьте сотруднику две роли и две группы. Группы не должны открывать административные страницы. Создайте/переименуйте роль и группу; отключенные справочники помечены текстом.
3. Первым администратором снимите системную роль у второго: следующий запрос его открытой сессии к администрированию должен дать 403, а «Мои задачи» оставаться доступными. Затем отключите сотрудника: его следующий запрос должен потребовать вход. Попытка отключить последнего администратора или системную роль должна отклониться без сохранения. Две открытые формы одного сотрудника: после сохранения первой отправка второй дает 409 и сохраняет ввод.
4. Откройте две сессии активного сотрудника и восстановите пароль через «Забыли пароль?»: ответ одинаков для существующего/несуществующего адреса, письмо есть только для активированного действующего аккаунта. После нового пароля старые сессии должны требовать вход. «Изменить пароль» сохраняет текущую сессию и отзывает остальные. Выход — кнопкой POST; GET `/accounts/logout/` не выполняет выход.

Этот сценарий предоставлен для ручного запуска человеком; автоматическая проверка через настоящий HTTP/SMTP приведена ниже. Полная браузерная приемка 360/1280 px пока не проводилась.

## Изолированная HTTP/SMTP проверка этапа 2

Скрипт создает синтетических сотрудников **только в отдельном пустом project** с префиксом `kp11-stage2-smoke-`; обычную БД не изменяет. Пароли генерируются случайно в памяти. Bootstrap, приглашения, активация, CSRF-формы, вход, запрет прямого POST, отзыв роли/доступа, reset и отсутствие использованных секретов в web logs проверяются настоящими запросами. Выберите новое имя project для каждого запуска, поскольку повторный запуск на непустой БД намеренно отклоняется:

```bash
export COMPOSE_PROJECT_NAME="kp11-stage2-smoke-$(date +%s)"
export WEB_PORT=18000 MAILPIT_PORT=18025 PUBLIC_BASE_URL=http://127.0.0.1:18000
docker compose up -d --wait db mailpit
docker compose run --rm migrate
docker compose up -d --wait web
python3 scripts/smoke_accounts.py --project "$COMPOSE_PROJECT_NAME" --web-port 18000 --mailpit-port 18025
docker compose down
unset COMPOSE_PROJECT_NAME WEB_PORT MAILPIT_PORT PUBLIC_BASE_URL
```

`down` оставляет тестовые named volumes; удаляйте их только по явно указанному имени одноразового тестового project, когда результаты больше не нужны. Для основной БД `down -v` не использовать. Перед этим сценарием выполните сборку образа по инструкциям выше. Браузер/JS engine этот скрипт не запускает.

## Ручная проверка этапа 3

После запуска и bootstrap по инструкции выше пригласите руководителя, сотрудника с двумя ролями/двумя группами и второго руководителя. Активируйте их через Mailpit и войдите в отдельных профилях браузера.

1. Руководителем откройте «Выдать задание» (`/workitems/new/`), введите задачу, срок и две подзадачи. Выберите одного сотрудника явно, обе его роли и обе группы. «Показать получателей» показывает его один раз и количество 1; подтвердите выдачу. Автор видит задание в «Выданных», сотрудник — в «Моих задачах». Автору личное назначение автоматически не создается.
2. Повторите POST подтверждения той же формы через возврат/обновление: открывается та же карточка. Откройте новое превью по группе, добавьте другого сотрудника в эту группу администратором и отправьте прежнее подтверждение. Получите 409 и новое превью; до повторного подтверждения выдачи нет. Удаление членства после выдачи не меняет созданные назначения.
3. Выдайте «Событие» с датой события, отличной от срока. Обе даты показаны отдельно по Москве; срок по дате — 23:59:59 выбранного дня. Задача не принимает дату события. Выполнение и редактирование доступны после этапа 4; чат будет на этапе 6.
4. Исполнитель читает карточку, но `/workitems/<UUID>/assignees/` и `/workitems/all/` дают 403. Второй руководитель без назначения получает 404 по UUID. Администратор читает «Все задания». Снимите роль у автора: карточка дает 404, повтор подтверждения — 403; собственное действующее назначение, если есть, остается основанием личного чтения.

Ручной сценарий человеком **не выполнен**. Автоматический сценарий ниже использует настоящий HTTP, cookies, CSRF, PostgreSQL и SMTP, но не браузер/JS engine.

## Ручная проверка этапа 4

После запуска и bootstrap пригласите руководителя и двух исполнителей, активируйте их через Mailpit и войдите в отдельных профилях браузера.

1. Выдайте задачу двум сотрудникам с двумя подзадачами. Первый отмечает один пункт: второй сохраняет пустой прогресс, завершение первого пока запрещено. Отметьте оба, нажмите «Выполнено»: у автора 1/2 = 50%, задача находится среди «Выполненных». «Вернуть» сохраняет отметки и дату предыдущего выполнения в истории; отметки завершенного назначения менять нельзя.
2. Автором поменяйте название/срок и порядок подзадач: выполнение сохраняется. Измените текст пункта или добавьте новый: проверьте список затронутых и число выполнений на превью, подтвердите сброс. Остальные отметки сохраняются. Если другой исполнитель завершит задание между превью и подтверждением, получите 409 и новые последствия. Удаление пункта сохраняет историю и не завершает незавершенное назначение автоматически.
3. Через «Все исполнители» отзовите назначение с причиной: сотрудник получает 404, статистика исключает его. «Добавить / восстановить» показывает совместимые отметки и возможность восстановления completion; подтвердите. Отключите второго сотрудника администратором и реактивируйте: назначение остается отозванным до явного восстановления автором.
4. Откройте две формы редактирования, сохраните первую и отправьте вторую: ожидается 409, ввод сохранен, новое превью обязательно. Архивируйте задание: текущие участники читают его через «Архив», действия выполнения/редактирования закрыты; отозванный участник доступа не получает. Автор читает ревизии/историю, исполнитель — свои действия без чужих отметок.

Ручной сценарий человеком **не выполнен**. Автоматические браузерные проверки 360/1280 px добавлены в этапе 5; фактические результаты — в STATUS.md.

## Изолированная HTTP/SMTP проверка этапа 4

Сначала соберите текущий образ. Для каждого полного запуска используйте новый пустой project; скрипт проверяет префикс и отсутствие сотрудников перед записью.

Проверяются настоящий HTTP/SMTP, CSRF/cookies, независимые отметки, completion/return, reorder/reset/reconfirm, revoke/restore, конфликт версий, отключение/реактивация, статистика/история и архив. Это не браузер/JS engine. `down` сохраняет тестовые volumes; основная БД не изменяется.

При несогласованных прямых изменениях БД миграция явно останавливается; не подменяйте историю и не запускайте обход ограничений.

## Браузерные проверки этапа 5

Проверяются реальные страницы Chromium, PostgreSQL, письма Mailpit, cookie/CSRF. Сценарии на 360 и 1280 px: приглашение/активация/вход, выдача, независимые отметки, выполнение/возврат, редактирование со сбросом, конфликт версий, отзыв/восстановление, архив, фильтры/вкладки и административные формы. Дополнительно: длинные ФИО/тексты, клавиатура/skip-link/видимый фокус, подписи полей/checkbox groups, текстовый контраст и отсутствие горизонтальной прокрутки. Без JavaScript проходят выдача/возврат из превью, отметки/выполнение/возврат и редактирование.

Инструменты проверки отдельны от runtime приложения: Python **3.12 Linux amd64**, Playwright **1.62.0** и установленные системные Chromium **151.0.7922.173** (`/usr/bin/chromium`). Browser lock фиксирует версии/хеши; в web-образ не входят browser venv и артефакты. Другие браузеры/OS/CPU не проверены.

```bash
python3 -m venv .venv-browser
PIP_CACHE_DIR="$PWD/.cache/pip-browser" PIP_CERT=/etc/ssl/certs/ca-certificates.crt .venv-browser/bin/python -m pip install --require-hashes -r requirements-browser.lock
/usr/bin/chromium --version

export COMPOSE_PROJECT_NAME="kp11-stage5-browser-$(date +%s)"
export WEB_PORT=18100 MAILPIT_PORT=18125 PUBLIC_BASE_URL=http://127.0.0.1:18100
docker compose up -d --wait db mailpit
docker compose run --rm migrate
docker compose up -d --wait web
.venv-browser/bin/python scripts/browser_stage5.py --project "$COMPOSE_PROJECT_NAME" --web-port 18100 --mailpit-port 18125 --chromium /usr/bin/chromium
docker compose down
unset COMPOSE_PROJECT_NAME WEB_PORT MAILPIT_PORT PUBLIC_BASE_URL
```

Сначала соберите текущий web-образ по командам выше. Для каждого полного запуска нужен **новый пустой project**: runner отказывает до bootstrap, если уже есть сотрудники. Он не удаляет данные. Не запускайте на обычной БД. `down` сохраняет тестовые volumes. Стандартный unittest runner сообщает количество, failures/errors/skipped и exit code; DOM/layout/contrast checks являются утверждениями внутри сценариев. `test-results/stage5/results.json` содержит текущий run_id, счетчики и результат каждого аудита; screenshots сохраняются только для синтетических рабочих страниц. Эти файлы игнорируются Git. Auth traces/HAR/videos и секретные URL/пароли в артефакты не записываются. Человеческая оценка внешнего вида и тесты assistive technology этим не заменяются.

Политика **Referrer-Policy: strict-origin** отправляет только origin без пути/query и позволяет Chromium корректно отправлять Origin при POST локальных HTTP-форм. Браузерный runner проверяет Origin/Referer реальных запросов активации; CSRF не отключается.

## Короткая ручная проверка этапа 5

После bootstrap и активации руководителя и двух исполнителей откройте их сессии в отдельных профилях браузера.

1. На 360 px и 1280 px выдайте задачу с длинными названием/описанием и двумя подзадачами. Проверьте превью и возврат к заполненной форме. Первый исполнитель отмечает пункты и выполняет задачу; у второго отметки независимы. «Выполнены» → «Вернуть» переносит назначение назад, сохраняя отметки.
2. Выдайте событие с отдельной датой; примените фильтры по автору/виду и обе сортировки срока. Проверьте ближайший и просроченный срок, пустой результат и сброс фильтров. Обычному исполнителю недоступны «Выданные», «Все задания» и чужой прогресс; руководитель видит свою статистику.
3. Добавьте/измените подзадачу с подтверждением сброса, откройте две формы для конфликта версий. Отзовите/восстановите исполнителя, затем архивируйте: чтение сохраняется у текущих участников, действий изменения нет.
4. Используя только Tab/Shift+Tab/Enter/Space, проверьте переход к содержимому, фокус и отметки. Введите ошибочный адрес приглашения и проверьте сохранение ФИО/выборов. Повторите выдачу и выполнение с выключенным JavaScript. На обеих ширинах основной экран не должен прокручиваться горизонтально.

Фактически выполненные автоматические проверки и непроверенные операции отдельно перечислены в STATUS.md; этот ручной сценарий человеком не выполнялся.

## Чат события: проверка этапа 6

Из карточки события доступен «Чат события». История — по 50 сообщений, «Предыдущие сообщения» использует before_id. Polling обновляет изменения каждые 10 секунд на видимой вкладке, с backoff до 60 секунд; состояние закрытия/архива и права перечитываются каждый раз. Видимые сообщения получают актуальные ФИО и активные группы автора, без email и чужого прогресса. Без JavaScript отправка и история работают обычными POST/GET; обновление — по ссылке.

Текст после удаления крайних пробелов содержит 1–4000 символов; HTML показывается текстом. POST отправки включает UUID request_key: одинаковый канонический ввод возвращает прежнее сообщение, другой ввод с тем же ключом дает 409. Доступ заново проверяется и для повтора. После скрытия повтор возвращает заглушку. Закрытие/архив запрещают новые сообщения всем; завершение личного назначения чат не закрывает. Лимиты фиксированных минутных окон: 10 сообщений на пользователя/событие и 30 на пользователя во всех событиях; 429 содержит Retry-After. Успешный повтор лимит не расходует.

Чтение не дает права отправки или модерации. Для внешнего читателя нужны отдельные send_accessible/moderate и доступное событие. Модерация в закрытом чате допустима, в архиве запрещена. Причина скрытия обязательна (до 500 символов). Оригинал не включается в обычные HTML/JSON/аудит; отдельная страница доступна только системному администратору с audit.view. Открыть чат обратно, редактировать сообщение, прикрепить файл или получить почтовое уведомление в V1 нельзя.

Для повторяемой browser-проверки нужна новая пустая БД, установленный .venv-browser из раздела этапа 5 и системный Chromium. Сначала выполните cloud-сборку из раздела запуска. Затем:

```bash
(
set -e
export COMPOSE_PROJECT_NAME="kp11-stage6-browser-$(date +%s)"
export WEB_PORT=18210 MAILPIT_PORT=18235 PUBLIC_BASE_URL=http://127.0.0.1:18210
trap 'docker compose down' EXIT
docker compose up -d --wait db mailpit
docker compose run --rm migrate
docker compose up -d --wait web
.venv-browser/bin/python scripts/browser_stage6.py --project "$COMPOSE_PROJECT_NAME" --web-port 18210 --mailpit-port 18235 --chromium /usr/bin/chromium
python3 scripts/smoke_chat_workers.py --project "$COMPOSE_PROJECT_NAME"
)
```

Runner отказывается от основного project/портов и от заполненной БД, активирует четырех синтетических сотрудников через Mailpit, выполняет 8 сценариев на 360/1280 px. В test-results/stage6/results.json записываются текущий run_id, результаты и проверки DOM/контраста; screenshots без auth traces/HAR/video. Большая история для пагинации создается через реальный service/аудит с отключенным лимитом только для fixtures; отдельные HTTP-проверки лимита его не отключают. smoke_chat_workers дополнительно запускает два отдельных Python-процесса с runtime DB-правами: 12 попыток в одной фиксированной минуте дают 10 сообщений, 2 отказа и ровно 10 receipts/записей аудита. Время окна фиксируется только в этой изолированной проверке; PostgreSQL quota/locks остаются настоящими. Повтор всей проверки требует новый project; down сохраняет volumes.

Короткая ручная проверка (человеком не выполнялась):

1. Выдайте событие двум исполнителям. В двух профилях откройте чат, отправьте обычный текст и `<script>alert(1)</script>`: код виден текстом, сообщение другого сотрудника появляется без перезагрузки. Проверьте группы автора, историю свыше 50 сообщений и работу отправки с выключенным JavaScript. Выполнение назначения должно оставить чат доступным.
2. Модератор с view_all + moderate скрывает старое сообщение с причиной. Открытая страница заменяет текст заглушкой на следующем polling. Модератор не видит оригинал и не может отправлять без назначения/send_accessible; администратор с audit.view читает оригинал отдельной страницей. Руководитель закрывает чат: история читается, новых отправок нет; архив запрещает и модерацию.
3. Отзовите назначение при открытом чате: следующий запрос очищает содержимое и останавливает polling. В DevTools повторите сохраненный POST — 404; до отзыва тот же ключ/текст не создает дубль, другой текст дает 409. Превысьте лимит — 429/Retry-After; пустой текст или 4001 символ — 400 при прямом POST. Прямой chat URL обычной задачи дает 404.

## Учетные записи БД и production-граница

На новом development volume init-скрипт создает `kp11_owner` (только bootstrap PostgreSQL), `kp11_migrator` (владелец схемы, DDL, CREATEDB для тестовой БД) и `kp11_app` (runtime, без SUPERUSER/CREATEDB/CREATEROLE/CREATE SCHEMA). Web получает только пароль `kp11_app`; bootstrap/migration-пароли в его окружение не передаются.

Сервис `migrate` запускает `prepare_database`: обычные Django migrations, затем `grant_runtime_access`. Эта повторяемая операция выдает DML/sequence-права, но запрещает runtime UPDATE/DELETE/TRUNCATE аудита, INSERT/DELETE guard, изменение django_migrations и DML каталога Permission. DB-triggers также защищают неизменяемые key/system-флаг роли, корпоративный email и административные разрешения от назначения обычной роли; права системной роли нельзя удалить. Дополнительный DB-trigger запрещает изменение/удаление строк аудита даже через прямой SQL владельца. Миграционная учетная запись — доверенная инфраструктурная власть, способная менять схему; она не используется HTTP-приложением.

Production settings находятся в `config/settings/production.py`: DEBUG=False, реальные SMTP/HTTPS hosts из окружения, Secure cookies, CSRF origins, STARTTLS, HSTS и безопасные заголовки. Они отклоняют очевидную тестовую почту, wildcard hosts, попытку включить DEBUG, тестовый email backend и неверный PUBLIC_BASE_URL. Recovery отвечает одинаково независимо от наличия аккаунта и ошибки SMTP; одинаковое время ответа не заявляется. Все лимиты хранятся в PostgreSQL и общие для workers; IP берется из REMOTE_ADDR, произвольный X-Forwarded-For игнорируется. Перед production настройте доверенную передачу IP и исключите секретные URL/тела форм из proxy access/error logs. `Dockerfile` по умолчанию запускает Gunicorn с двумя workers от пользователя 10001; development Compose явно переопределяет это на runserver.

Production Compose/proxy, реальный SMTP, внешний HTTPS и backup/restore выполняются на этапе 7; сейчас они **не проверены**. Development Compose/.env нельзя считать production-развертыванием. В production миграционную роль создают без CREATEDB, пользователь приложения не получает bootstrap/migration-секретов; реальные домены, DB/SMTP credentials и ключи задаются через защищенные настройки. Резервные копии и восстановление описаны как проектное решение в ARCHITECTURE, не как уже выполненная операция.
